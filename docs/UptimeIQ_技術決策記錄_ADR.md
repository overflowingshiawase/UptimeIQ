# UptimeIQ 技術決策記錄（Architecture Decision Records）

> 本文件記錄 UptimeIQ 開發過程中的關鍵架構決策、考慮過的替代方案，以及各項取捨的代價。目的是讓評估者（面試官、技術主管）理解「為什麼這樣設計」，而不只是「做了什麼」。

---

## ADR-001：採用 Supabase（BaaS）而非自建後端框架

**背景**
個人獨立開發、時程有限，需要在短時間內驗證產品核心邏輯（動態保養排程、異常診斷）是否成立，而非優先追求架構完整度。

**決策**
採用 Supabase 作為 Backend-as-a-Service，前端 JavaScript 直接呼叫 Supabase Client SDK，資料存取與權限控管交由 Supabase 內建的 PostgreSQL + Row Level Security 處理。

**考慮過的替代方案**
自建 Node.js／FastAPI 後端 + 獨立 PostgreSQL 資料庫，前端透過自訂 REST API 存取資料。

**取捨與代價**
- 換到的好處：開發速度大幅提升，資料庫 Schema 變更後前端可立即串接，不需要額外維護 API 層。
- 付出的代價：商業邏輯被分散在「前端呼叫邏輯」與「資料庫 RLS Policy」兩層之間，而非集中在單一 Service Layer，長期來看不利於複雜商業規則的維護與單元測試。
- **何時該重新評估**：當系統需要處理跨表交易（transaction）、第三方系統 webhook 簽章驗證，或多步驟工作流編排時，會考慮導入 FastAPI 作為中介服務層，Supabase 退居純資料庫角色。

## ADR-002：權限控管下放至資料庫層（RLS），而非僅在前端限制

**背景**
系統需要區分 admin（可見完整績效分析）與 viewer（僅可見基本資料）兩種角色，且權限判斷需要在資料存取的最底層就生效，避免前端邏輯被繞過的風險。

**決策**
使用 Supabase Row Level Security，將權限規則寫在資料庫 Policy 層，搭配 `user_profiles` 角色表判斷存取權限。

**考慮過的替代方案**
僅在前端做條件渲染（隱藏 UI 元件）+ 後端 API 做角色驗證。

**取捨與代價**
- 換到的好處：即使前端程式碼被繞過或直接呼叫 API，資料庫層仍會擋下未授權存取，屬於縱深防禦（Defense in Depth）設計。
- 付出的代價：RLS Policy 的除錯成本較高，每條新增的 Policy 都需要用不同角色的測試帳號實際驗證，且邏輯藏在資料庫層，不像應用層程式碼那樣容易做 Code Review。
- **何時該重新評估**：當角色種類超過 3-4 種、或權限規則出現「同一資源依不同條件有不同存取層級」的複雜情境時，目前這種 Policy-per-table 的方式會變得難以維護，需要改為更結構化的權限模型（例如獨立的 role-permission join table）。

## ADR-003：以 n8n 而非自建排程服務處理自動化流程

**背景**
系統需要兩條自動化流程：異常自動診斷推播、班別交接自動結構化，兩者都涉及「規則計算 → 呼叫 LLM API → 推播通知」的固定流程。

**決策**
使用 n8n 進行工作流編排，呼叫 Google Gemini API 做內容生成，並將結果推播至 Discord Webhook。

**考慮過的替代方案**
自行撰寫 Python 排程腳本（cron job）搭配 API 呼叫。

**取捨與代價**
- 換到的好處：流程節點可視化，非工程背景的 PM／BA 也能理解自動化邏輯；workflow 可直接匯出成 JSON 供稽核與版本留存。
- 付出的代價：核心業務邏輯有一部分存在於 n8n 平台的視覺化節點中，而非純程式碼，版本控制與 Code Review 的體驗不如純程式碼直覺，且系統對 n8n 這個第三方服務的穩定性有一定依賴。
- **何時該重新評估**：當自動化流程數量增加、且流程之間出現複雜的條件分支或需要跨流程共用邏輯時，會考慮將核心規則計算邏輯抽離成獨立的 Python 套件，n8n 只負責觸發與通知。

## ADR-004（Future）：多租戶架構尚未實作

**背景**
UptimeIQ 目前的產品定位是「可販售給任何製造業客戶的 B2B 保養管理產品原型」，但現有資料庫僅有 admin／viewer 兩種角色，尚未有 organization（租戶）層級的資料隔離。

**決策（規劃中，尚未實作）**
若要正式走向多租戶 SaaS，需要在 `machine_master` 等主要資料表中加入 `organization_id` 欄位，並在對應的 RLS Policy 中加入租戶比對條件，確保 A 公司無法查詢 B 公司的設備資料。

**為什麼現階段不做**
MVP 階段的優先目標是驗證核心保養排程與異常診斷邏輯本身是否成立，過早導入多租戶架構會增加不必要的複雜度，且在沒有真實客戶驗證需求前，租戶隔離的設計容易做錯方向。

**觸發重新設計的時間點**
當專案取得第一個真實試用客戶、且第二個客戶也表達使用意願時，即為導入多租戶架構的合理時間點。
